# TETR.IO Client Dissection — Input, Handling, Piece Physics

Source: official production client contained in `01_Official_Standalone`.
Engine version observed in this build: **19**.

This document uses semantic names inferred from behavior. Original minified manager/property names are shown where useful.

## 1. Simulation model

The gameplay core advances on a **fixed 60 Hz simulation step** (`1/60 s`). Rendering is separate from gameplay simulation.

High-level frame pipeline:

```text
Pull queued replay/network/input events
→ advance event stream frame
→ process horizontal shift (DAS/ARR)
→ advance falling-piece gravity / lock state
→ process interrupt actions (rotate / hold / hard drop, etc.)
→ process waiting-frame events
→ garbage-ARE / objective / attack bookkeeping
→ actors / visual state updates
→ next simulation frame
```

Keyboard events retain **subframe order**. Event timestamps are quantized to 0.1 simulation frame, roughly **1.67 ms** at 60 Hz. Browser `keydown` auto-repeat is ignored; repeat behavior is generated by the game engine itself.

## 2. Default handling values

Observed defaults:

| Option | Default | Meaning |
|---|---:|---|
| ARR | 2 F | repeat interval after DAS |
| DAS | 10 F | delayed-auto-shift charge |
| DCD | 2 F | DAS cut after wall-state actions |
| SDF | 6 | soft-drop factor |
| safelock | true | short hard-drop protection after natural lock |
| cancel | false | opposing-direction release reset behavior |
| may20g | true | handling may enter 20G where rules allow |
| IRS | tap | initial rotation system |
| IHS | tap | initial hold system |

Handling bounds in this client:

```text
ARR: 0..5 frames, 0.1 precision
DAS: 1..20 frames, 0.1 precision
DCD: 0..20 frames, 0.1 precision
SDF: 5..41 (41 is the special "infinite" value)
IRS/IHS: off | hold | tap
```

## 3. Horizontal movement: DAS / ARR

The engine tracks left and right independently, with a `lastshift` direction deciding which side wins if both are held.

On initial left/right keydown:

```text
mark direction held
set it as lastshift
perform one immediate horizontal move
start DAS charge
```

Autorepeat behavior:

```text
while held and direction == lastshift:
    charge DAS until handling.das
    once charged:
        accumulate ARR
        emit floor(accumulatedARR / handling.arr) shifts
```

Special case: **ARR = 0**. The engine attempts up to board width shifts in the same update, effectively snapping the piece to the wall.

### Simultaneous left/right

The most recently pressed direction wins. Releasing the currently active direction transfers priority to the other direction if it is still held.

### `cancel` handling option

With `cancel=true`, releasing one direction can reset the opposing direction's shift timers. This is separate from normal last-input priority.

## 4. DCD (Delayed Auto Shift Cut)

DCD is real engine behavior, not merely a settings label.

When the piece is in the engine's **wall state**, certain actions call an internal DCD routine. With DCD > 0, both horizontal DAS counters are clamped to approximately:

```text
DAS_charge = min(current_charge, DAS - DCD)
ARR_charge = ARR
```

With defaults DAS=10, DCD=2, a fully charged wall DAS becomes at most 8 frames of charge, requiring about two simulation frames before full DAS resumes.

The DCD routine is called after successful rotation and around next-piece transition logic. This is one reason TETR.IO's wall handling differs from simplistic browser clones that only implement DAS+ARR.

## 5. Hoisted / pre-held inputs

The event stream remembers keys already held when gameplay begins or transitions. These are injected as **hoisted keydowns**.

For a hoisted horizontal input, DAS begins near:

```text
DAS - DCD
```

rather than from zero. This provides precharge-like behavior across relevant transitions while still respecting DCD.

## 6. IRS / IHS

TETR.IO implements both tap-style and hold-style initial actions.

### IRS tap

If rotation occurs while the falling piece is in its sleeping/pre-spawn state, the engine accumulates an `irs` rotation value instead of rotating a live piece. That rotation is applied on spawn.

### IRS hold

At spawn, currently held CCW/CW/180 buttons are combined into the initial rotation request.

### IHS tap

A hold press during the pre-spawn sleeping state records an IHS action, which is consumed when the new piece appears.

### IHS hold

If Hold remains down at spawn and IHS is configured to hold, the engine immediately performs hold on the spawning piece.

The renderer also previews some IRS/IHS outcomes while the piece is sleeping, so this behavior is integrated into both simulation and display.

## 7. Gravity

Gravity is expressed in **cells per simulation frame**.

For 40 LINES this build uses:

```text
g = 0.02 cells/frame
```

At 60 Hz:

```text
0.02 × 60 = 1.2 cells/second
```

This confirms gameplay gravity is not tied to monitor refresh rate.

### Soft drop

For engine v19 and a `Fall(dt)` call, finite soft drop uses exactly:

`max(effectiveGravity * dt * SDF, 0.05 * SDF)`

The `0.05 * SDF` floor is **not multiplied by `dt`**, so low-gravity subframe splits preserve a call-boundary quirk.

SDF=41 is the v15+ infinity sentinel and uses `400 * dt`, not a literal 41× multiplier. See `TETRIO_FALL_SOFTDROP_ANTISTALL_EXACT_V19.md` for exact testable semantics.

## 8. 20G

Current engine logic recognizes 20G when effective gravity reaches/exceeds board height, subject to mode and handling permissions.

`may20g` gates handling-driven 20G behavior. Modes can also disable gravity-based 20G (`gravitymay20g=false`, for example in the observed BLITZ configuration).

At 20G, the piece is slammed to its lowest legal vertical position as part of spawn/movement handling rather than merely falling one cell at a time very quickly.

## 9. Lock delay and reset system

Observed standard defaults:

```text
locktime = 30 frames ≈ 0.5 seconds
lockresets = 15
```

Successful lateral movements and rotations can increment reset counters. When the piece reaches a genuinely new low vertical position, movement/rotation reset counters are cleared unless infinite movement is enabled.

The engine separately tracks movement resets and rotation resets. Exact v19 fall-speed anti-stall begins when `piece.rotresets > lockresets + 15` and adds `0.5 * dt * (rotresets - (lockresets + 15))` to that `Fall(dt)` call's budget. A separate kick-Y-base switch uses `totalRotations`, not `rotresets`; do not merge the two counters.

## 10. Safelock

With `safelock=true`, a naturally locking piece sets a short safelock value on transition. The next piece inherits this protection for several frames, during which hard drop is refused.

Observed value after natural lock:

```text
safelock = 7 frames
```

This prevents accidental buffered hard drops from instantly killing the next piece. A hard-drop lock itself follows a different path and does not set this protection in the same way.

## 11. Hard drop

Hard drop repeatedly advances the piece downward until the next step would collide, awards hard-drop distance scoring, then locks the piece.

It is blocked while safelock is active.

## 12. Rotation / kick resolution

The core rotation path can be summarized as:

```text
ComputeKick(piece, x, y, oldRotation, newRotation)
    apply piece rotation offsets
    test pure rotation
    if illegal:
        select piece-specific kick table
        iterate kick offsets in order
        return the first legal result
```

The production client contains explicit kicksets including **SRS** and **SRS+**.

### SRS+ difference found in this build

For ordinary JLSTZ kick data, SRS and SRS+ are largely shared. The major explicit difference is the **I-piece** kick table, including reordered/symmetrized 90° behavior and extra 180° one-cell offsets.

Observed SRS+ I-piece 180 offsets include:

```text
0 → 2 : (0, -1)
1 → 3 : (+1, 0)
2 → 0 : (0, +1)
3 → 1 : (-1, 0)
```

This is useful evidence that the local official client is running actual TETR.IO SRS+ rather than a clone's approximate SRS implementation.

## 13. Spin-state persistence

Rotation/spin state is not permanent until lock. Certain subsequent actions clear it.

Notably, horizontal movement and reaching a new integer vertical row can clear rotation/spin flags. This supports the usual "rotation must remain the relevant last action" character of spin recognition.

## 14. Finesse calculation

The client contains a precomputed finesse table for all seven tetrominoes, indexed by piece type, rotation and destination x.

`piece.keys` is incremented approximately as:

```text
initial horizontal press: +1
90° rotation: +1
180° rotation: +2
hard drop: +0
```

At placement, the engine compares actual key count against the table's minimal expected count:

```text
faults = max(0, actualKeys - idealKeys)
```

It tracks finesse combo, faults and perfect pieces. Soft-dropped pieces receive special treatment and do not produce normal finesse faults through this path.

## 15. Why this matters for the local build

For `01_Official_Standalone`, the code governing all of the above is the official production gameplay client. The local wrapper does not need to reproduce these mechanics; it only needs to let the official client initialize and satisfy the services/assets it expects.

That is materially different from the lightweight clone, where DAS, rotation, gravity and scoring were independently reimplemented and can diverge.
